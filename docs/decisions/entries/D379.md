## D379: a new decision is its own file, and its status line is its Index row

- Status: active
- Date: 2026-11-06 (the owner, twice in a day: "merge conflicts are there", then "conflicts again", on #719)
- Decision: from D379 a decision is one file, `docs/decisions/entries/Dn.md`, with a `- Status:` line (the status words in the README). `scripts/docsCheck.mjs` builds that decision's Index row from it, so every check that reads rows (an entry has a row, a "supersedes" names a decision that exists, a retired decision says so) reads it too. Decisions to D378 keep their area files and README rows; a decision that amends or retires one of them still edits that old row.
- Why: every decision added a row on the last line of the README Index and an entry at the end of an area file, so any two pull requests that each added a decision conflicted on both, and the owner met it in the merge button. A `merge=union` attribute would not have helped: GitHub's server-side merge ignores `.gitattributes` merge drivers. One file per decision leaves nothing shared to collide on.
- Cost: a new decision has no row in the README table, so the table alone no longer lists them all; `grep -rn "keyword" docs/decisions/` still finds both, and `entries/` holds the newest. The check reads one more directory.
- Rejected: `merge=union` (GitHub ignores it); an Index generated into the README (the generated file would itself be edited by every pull request); moving the 376 old entries into files (a large rewrite for no conflict they still cause).
- Revisit if: a decision pull request still conflicts on the record, or a session cannot find a new decision by grep.
