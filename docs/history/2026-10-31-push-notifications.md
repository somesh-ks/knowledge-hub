# 2026-10-31: a ping when a Catch up or a regeneration ends (D284)

The owner said yes to push notifications (PWA-05 in the backlog). D11 had left web push to a later feature; this is stage 2 of the staged plan: only runs the device itself started, no accounts.

- Design: the cancel token (D242) already says which device started a run, so it is also the proof that lets a device ask to be told about that run. The browser's push address goes to Neon (`push_watches`, two per run, six hours). `content.yml` sends after its sync, because the episode is in the store by then; the run is known to be over by its `pipeline_runs` row (D221), which the engine writes whatever the end. No new server, queue or poll.
- Scope grew in the thread: the owner asked for its own menu with Daily, Weekly and Podcast ready, and a global switch that goes mixed. Daily and Weekly are a per-device list (`push_devices`), claimed once per published run. The mixed Switch is a design-system change (`:indeterminate`), shipped in the DS PR that carries the select-sheet guard. Left out: a message per stage, any ping for a run another device started; "other things" waits for the owner to name them.
- Checked: a PGlite test of the whole path (cap of two per run, once per ended run, 410 dropped, a down push service retried, old and empty runs swept), a handler test of the token and address checks, and the Settings page at 390 and 1280. Not checked on a real device: permission from a select's change on iOS, delivery to the Home Screen app, the tap opening the episode. The Settings page was first a Notifications page with a dropdown under Sound; the owner asked for its own section and a switch, and asked why he had to make keys and set secrets, so the site now makes the key pair itself.
- Gotcha to carry: the private key sits in Neon beside the config, so whoever holds `DATABASE_URL` could send as the site. That is no new power: they could already rewrite the config.
